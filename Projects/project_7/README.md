# Project 7 — First ROS 2 Nodes (PX4 Telemetry over uXRCE-DDS)

A ROS 2 Jazzy Python package containing two subscriber nodes. The second one reads
live position and velocity estimates from a PX4 flight controller running in SITL,
bridged into ROS 2 over uXRCE-DDS.

This is the project where the work moves from standalone Python scripts using MAVSDK
to nodes running inside the ROS 2 framework — the architecture real drone autonomy
stacks are built on.

---

## Contents

```
my_first_node/
├── package.xml                    ROS package manifest (identity + dependencies)
├── setup.py                       Python packaging + entry points
├── setup.cfg
├── resource/my_first_node         Package marker file for the ROS index
├── test/                          Auto-generated lint tests (flake8, pep257, copyright)
└── my_first_node/
    ├── __init__.py
    ├── listener.py                Node 1 — subscribes to /chatter (std_msgs/String)
    └── px4_listener.py            Node 2 — subscribes to PX4 local position
```

### Node 1 — `listener`

Subscribes to `/chatter` carrying `std_msgs/msg/String` and logs each message.
Used with the ROS 2 demo talker to verify the package builds and pub/sub works.

### Node 2 — `px4_listener`

Subscribes to `/fmu/out/vehicle_local_position_v1` carrying
`px4_msgs/msg/VehicleLocalPosition` and logs position (`x`, `y`, `z`) and
velocity (`vx`, `vy`, `vz`) in the NED frame.

PX4 publishes this topic at **50 Hz** (observed ~20 ms between messages).

## Build from a fresh clone

This repository stores the **package source only**. The `build/`, `install/`, and
`log/` directories are build artifacts generated by `colcon` and are intentionally
not committed — you generate them yourself.

### 1. Create a ROS 2 workspace (if you don't have one)

```bash
mkdir -p ~/ros2_ws/src
```

### 2. Copy the package into the workspace

```bash
cp -r Projects/project_7/my_first_node ~/ros2_ws/src/
```

### 3. Source the ROS 2 underlay

```bash
source /opt/ros/jazzy/setup.bash
```

### 4. Build

```bash
cd ~/ros2_ws
colcon build
```

### 5. Source the workspace overlay

```bash
source install/setup.bash
```

> Required in **every new terminal** that wants to run these nodes. Without it,
> `ros2 run` reports that the package cannot be found, even though the files exist
> on disk. Sourcing the overlay is what makes the built package discoverable.

### 6. Verify the executables are registered

```bash
ros2 pkg executables my_first_node
```

Expected:
```
my_first_node listener
my_first_node px4_listener
```

## Running `px4_listener` (requires SITL + bridge)

Start these in order. Each needs its own terminal.

**Terminal A — Micro XRCE-DDS Agent:**
```bash
MicroXRCEAgent udp4 -p 8888
```

**Terminal B — PX4 SITL:**
```bash
cd ~/PX4-Autopilot
make px4_sitl gz_x500
```

Wait for PX4 to connect to the agent (the agent logs new client sessions).

**Terminal C — verify the topic exists before running any code:**
```bash
source /opt/ros/jazzy/setup.bash
source ~/ros2_ws/install/setup.bash

ros2 topic list | grep vehicle_local_position
ros2 topic echo /fmu/out/vehicle_local_position_v1
```

If `echo` streams data, the bridge is working. Only then run the node:

```bash
ros2 run my_first_node px4_listener
```

Expected output:
```
[INFO] [...] [px4_listener]: x=0.00 y=-0.02 z=-0.03 vx=-0.01 vy=-0.02 vz=-0.00
```

Values near zero with `z` slightly negative are correct for a drone sitting on the
ground — in the NED frame, `z` is positive **downward**, so a small negative `z`
means marginally above the reference altitude. The jitter is EKF/sensor noise.

## QoS — the critical gotcha

PX4 publishes with **BEST_EFFORT** reliability and **TRANSIENT_LOCAL** durability.
The ROS 2 default is `RELIABLE` + `VOLATILE`.

A subscriber's requested QoS must be **equal to or weaker than** what the publisher
offers, or no connection is established. Critically, an incompatible QoS produces
**no messages and no error** — the node runs silently forever, appearing broken for
no visible reason.

`px4_listener` therefore builds its profile explicitly:

```python
qos_profile = QoSProfile(
    reliability=ReliabilityPolicy.BEST_EFFORT,
    durability=DurabilityPolicy.TRANSIENT_LOCAL,
    history=HistoryPolicy.KEEP_LAST,
    depth=5,
)
```

To inspect any publisher's QoS yourself:
```bash
ros2 topic info /fmu/out/vehicle_local_position_v1 --verbose
```

Only **reliability** and **durability** affect compatibility. History and depth
control buffering, not whether a connection forms.

## Versioned topic names

This PX4 build uses **versioned** topic names — note the `_v1` suffix on
`/fmu/out/vehicle_local_position_v1`. Older tutorials reference the unversioned
`/fmu/out/vehicle_local_position`, which does not exist here. Subscribing to a
non-existent topic fails silently, exactly like a QoS mismatch.

Always confirm against your own system before writing a subscriber:

```bash
ros2 topic list                                          # find the real name
ros2 topic info <topic_name>                             # get the message type
ros2 interface show px4_msgs/msg/VehicleLocalPosition    # get every field name
```

## Troubleshooting

**`Package 'my_first_node' not found`**
The workspace overlay isn't sourced. Run `source ~/ros2_ws/install/setup.bash`.

**`No executable found`**
The node isn't registered in `setup.py` under `entry_points`, or the workspace
wasn't rebuilt after adding it. Entry points map an executable name to a module and
function — e.g. `'px4_listener = my_first_node.px4_listener:main'`. No file paths,
no `.py` extension, and the `:main` is required.

**Node runs but logs nothing**
Almost always one of three things:
1. QoS mismatch (see above)
2. Wrong message type — publisher and subscriber must agree on type as well as
   topic name. Check with `ros2 topic info <topic>`; if it lists two types, one of
   them is your mis-typed subscriber.
3. Wrong topic name — check the `_v1` suffix

**`ModuleNotFoundError: px4_msgs`**
`px4_msgs` isn't installed or isn't sourced. It must also be declared in
`package.xml` as `<depend>px4_msgs</depend>`.

## Concepts covered

- **Node** — a long-lived program that joins the ROS graph and communicates over
  topics, as opposed to a script that runs once and exits
- **Topic** — a named channel carrying exactly one message type; publishers and
  subscribers are fully decoupled and only agree on name + type
- **`rclpy.spin()`** — the event loop that keeps the node alive *and* dispatches
  callbacks (incoming messages, timers, service calls). Callbacks only execute
  because spin invokes them
- **Inheritance** — `class PX4Listener(Node)` inherits all of `Node`'s capabilities;
  `super().__init__('px4_listener')` runs the parent's setup, registering the node
  with the ROS graph
- **`ros2 run` vs `python file.py`** — `ros2 run` resolves a *package* + *executable*
  through the built install space, requiring `colcon build` and a sourced overlay.
  No filesystem paths, so launch files remain portable
- **QoS** — quality-of-service contracts that must be compatible for a connection
  to form
